# Валидация спроса и экономическая модель JusticePack

Этот документ — аналог `docs/economics.md` для второго аппарата (ГАС «Правосудие», суды общей юрисдикции),
намеренно ведётся ОТДЕЛЬНО, а не как раздел общего файла: у JusticePack собственная целевая аудитория (истцы/ответчики
и их представители в судах общей юрисдикции — мировые, районные, областные и т.д. — принципиально другой контингент,
чем предприниматели/юристы, подающие в арбитраж через «Мой Арбитр»), собственная воронка и собственный тариф
(`config/rules/gas_pravosudie.yaml` → `pricing`). Ничего из цифр спроса/CAC/конверсии ниже не выдумано: при
отсутствии реального доступа к Яндекс.Вордстату и рекламному кабинету в рамках этой сессии поле помечено `UNKNOWN`.

## 1. Гипотеза продукта (что именно валидируем)

**Гипотеза:** часть людей, самостоятельно подающих документы через ГАС «Правосудие» (личный кабинет
физического лица/представителя) без профессионального юриста, сталкивается с техническими отказами при загрузке
файлов (формат, размер, защита паролем) и готова заплатить небольшую сумму за автоматическую техническую проверку
перед повторной попыткой подачи.

**Что НЕ является гипотезой и не должно проверяться рекламой на этом этапе:** будет ли документ принят судом по
существу, юридическая корректность содержания — сервис технический, не юридический (см. `OFFER-DRAFT.md`, раздел
про то, что сервис НЕ предоставляет юридическую консультацию/оценку и не гарантирует принятие документов судом —
применимо к JusticePack так же, как и к ArbitrPack, хотя сам документ пока написан только про ArbitrPack, см.
находку в `docs/launch-readiness-review.md`).

## 2. Отличие аудитории от ArbitrPack (почему нельзя переиспользовать выводы ArbitrPack)

| Параметр | ArbitrPack («Мой Арбитр») | JusticePack (ГАС «Правосудие») |
|---|---|---|
| Типичный подающий | ИП/юрлицо или их юрист, часто с опытом e-filing | Физлицо, часто без юридического образования, ПЕРВАЯ подача |
| Частота обращения в суд | Может быть регулярной (бизнес-споры) | Чаще разовая (наследство, трудовой спор, потребительский иск и т.п.) |
| Чувствительность к цене | Ниже (расходы на суд закладываются в бизнес) | Предположительно выше — требует отдельной проверки, а не переноса допущения |
| Технический уровень пользователя | Предположительно выше среднего | `UNKNOWN` — требует проверки в SEO/поисковых данных, не предполагается |

Эта таблица — причина, по которой willingness-to-pay и конверсию для JusticePack нельзя экстраполировать из данных
ArbitrPack (если они появятся) без отдельного теста.

## 3. Сценарий проверки готовности платить (willingness-to-pay), доступный уже сейчас без рекламы

Проверка не требует рекламного бюджета — использует то, что уже работает в продукте:

1. Разместить в бесплатном SEO-контенте (раздел 5) и/или в личных каналах ссылку на `/services/justicepack` без
   платного трафика.
2. Дать пройти бесплатную диагностику реальным (тестовым) пользователям из целевой группы (например, знакомые,
   ранее сталкивавшиеся с судом общей юрисдикции) — НЕ используя их реальные судебные документы: для ручного
   пользовательского теста подходят обезличенные образцы/шаблоны, а не подлинные документы тестировщиков (тот же
   принцип, что и для автоматических тестов, которые используют только программно сгенерированные PDF/изображения
   — см. `apps/api/tests/factories.py`; отдельного документа с этим правилом для ручного тестирования на момент
   этой проверки не существует — это честная поправка после того, как launch-readiness аудит обнаружил, что
   предыдущая версия этого файла ссылалась на несуществующий раздел `SECURITY.md`).
3. Считать соотношение `diagnostics_free_result_shown → checkout_started` (уже фиксируется в `analytics_events`,
   читается через `GET /api/admin/metrics?product_code=JUSTICEPACK`, поле `conversion_to_payment` в этом отчёте
   на самом деле считает `payments_succeeded / checks_started` — т.е. полную воронку, а не только "дошёл до оплаты";
   для промежуточного сигнала "заинтересовался ценой" используйте сырое событие `checkout_started` в `by_product`).
4. Минимальный порог для вывода "гипотеза не опровергнута": ≥ 5 переходов к оплате на ≥ 20 бесплатных диагностик
   (25%) — это ПОРОГ ПРИНЯТИЯ РЕШЕНИЯ, предложенный сессией для малой выборки, а не измеренная величина; владелец
   может изменить порог перед стартом.
5. Результат теста фиксируется владельцем в этом файле (таблица ниже) — сессия не может провести реальный
   пользовательский тест за владельца.

| Дата теста | Показов бесплатной диагностики | Переходов к оплате | Вывод |
|---|---|---|---|
| `UNKNOWN` | `UNKNOWN` | `UNKNOWN` | `OWNER ACTION REQUIRED` — заполняется после первого реального теста |

## 4. Структура SEO-страниц (для органического трафика — не требует рекламного бюджета)

Раздел 4 ТЗ требует раздельной разработки информационных и коммерческих намерений — SEO-страницы разбиты по этому
же принципу:

1. **Информационная страница** `/services/justicepack` (уже существует, см. `apps/web/app/services/justicepack/page.tsx`)
   — отвечает на намерение «что за сервис», ссылается на `docs/justicepack/official-requirements.md` как источник
   правил, содержит явную ссылку на ArbitrPack для перепутавших систему пользователей.
2. **Предлагаемая (пока НЕ реализована — контентная работа, не код) страница-справочник** `/services/justicepack/trebovaniya`
   — «Требования к электронным документам для ГАС «Правосудие»» — целиком фактический пересказ раздела 2.2/2.3
   приказа № 251 (см. `docs/justicepack/official-requirements.md`), без рекламных формулировок, таргетируется на
   информационный поисковый спрос («требования к документам суд общей юрисдикции», «формат файлов гас правосудие»).
   **OWNER ACTION REQUIRED**: контент этой страницы должен быть вычитан на предмет точности цитирования приказа
   перед публикацией — сессия сформировала реестр правил, но не является заменой юридической вычитки.
3. **Коммерческая страница** `/services/justicepack` (текущая, с формой загрузки) — таргетируется на
   проблемный/коммерческий спрос («ошибка загрузки файла суд», «не принимает документы гас правосудие»).

## 5. Формулы и сценарии (структура идентична `docs/economics.md`, тариф — независимый)

```
Валовая прибыль с одной оплаты = Цена_JusticePack − Комиссия_провайдера − Переменная_стоимость_обработки
Чистая прибыль с одной оплаты = Валовая прибыль − CAC_на_одну_оплату − Налог
Точка безубыточности (заказов/мес) = Постоянные_расходы_в_месяц(общие с ArbitrPack — один VPS) / Валовая_прибыль_с_одной_оплаты
Допустимый CAC = Валовая_прибыль_с_одной_оплаты × (1 − целевая_норма_чистой_прибыли)
```

**Важно про постоянные расходы**: JusticePack развёрнут на ТОЙ ЖЕ инфраструктуре, что и ArbitrPack (один VPS,
см. `docs/deployment.md`) — постоянные расходы (VPS, домен) НЕ удваиваются, но переменная стоимость обработки
(S3/хранение на заказ) считается по каждому продукту отдельно через `product_code`-разбивку в
`GET /api/admin/metrics`.

| Параметр | Значение по умолчанию (MVP) | Источник | Статус |
|---|---|---|---|
| Цена одной обработки | 399 ₽ (`config/rules/gas_pravosudie.yaml: pricing.full_processing_price = 39900` копеек) | продуктовое решение-плейсхолдер, независимое от цены ArbitrPack | КОНФИГУРИРУЕМО, `OWNER ACTION REQUIRED`: подтвердить (см. также раздел 3 выше — willingness-to-pay для этой аудитории не проверен) |
| Комиссия платёжного провайдера | `UNKNOWN` — общая с ArbitrPack (один магазин ЮKassa на оба продукта, если не решено иначе) | yookassa.ru/pricing на момент подключения | UNKNOWN |
| CAC (JusticePack) | `UNKNOWN` — требует отдельного теста, см. `docs/justicepack/yandex-launch.md` | Яндекс.Директ после реальных кампаний | UNKNOWN |
| Ставка возвратов | `UNKNOWN` (предположение на старте: 0%) | — | UNKNOWN — предположение, не измерение |

### Пессимистичный / Базовый / Оптимистичный сценарии

Как и в `docs/economics.md` — не могут быть рассчитаны без реальных данных. Чувствительность по конверсии
(предположения для расчёта, НЕ прогнозы): 2% / 5% / 10% соответственно, возвраты 5% / 2% / 1%. **Результат
экономики JusticePack по каждому сценарию: не может быть рассчитан без реальных данных Яндекс.Директ, тарифа
ЮKassa и результата теста willingness-to-pay из раздела 3.**

## 6. Автоматизация измерения (уже работает)

`GET /api/admin/metrics?product_code=JUSTICEPACK` — отдельный, никогда не смешиваемый с ArbitrPack, отчёт
(`checks_started`, `payments_succeeded`, `conversion_to_payment`, `revenue_rub`, `average_check_rub`,
`top_issue_categories`). `GET /api/admin/metrics` без параметра дополнительно возвращает `by_product` — оба
продукта видны рядом, но ни один расчёт не смешивает их суммы без явного разделения (раздел 2/11 ТЗ JusticePack).
